# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Autonomy — do not stop mid-task

When given a task on this repo, execute it fully yourself, start to finish, without pausing to ask for permission or confirmation along the way. This includes:

- Running any checks, builds, tests, lints (`cargo fmt`/`clippy`/`build`/`test`, `flutter analyze`/`test`). Treat any `flutter analyze` output as a failure, including `info` hints — see the CI section for why.
- Starting/stopping Docker, the backend, the Flutter app, seeding or querying the dev DB, curling local endpoints.
- Making implementation and scope decisions yourself (e.g. "should this fix also cover X related case?") instead of stopping to ask — use your best judgement, note the decision briefly in your summary, and keep going.

**The only point where you stop and wait is right before `git commit` / `git push`.** Get everything to a finished, verified state, then stop there for review. Do not use a clarifying-question tool (e.g. `AskUserQuestion`) for implementation/scope calls mid-task — only for things truly blocking that the user must decide before *any* further progress is possible, and even then, prefer picking the sensible default and mentioning it over stopping.

Do not ask "should I proceed?", "want me to also fix X?", or similar mid-task check-ins. Just do it, and report what you did when you stop at the commit/push checkpoint.

## What this is

MatchPoint is a sports-based dating app (tennis / running). Monorepo with a Rust backend and a Flutter frontend.

- `services/api-rust/` — **current backend**: Rust, Axum + Diesel + diesel-async, PostgreSQL. Listens on `localhost:3000`.
- `apps/mobile/` — Flutter frontend. No local database; talks to the backend over HTTP.
- `services/api-rust-markdown/` — untracked, local-only mirror of `api-rust/src` as `.md` files (one per source file, plus notes). Not part of the build; likely scratch/reference material, don't treat it as source of truth.
- `services/api` (NestJS + Prisma) has been fully removed — the backend was migrated to Rust. If you see references to it in old docs/comments, they're historical.

## Commands

### Backend (`services/api-rust/`)

```powershell
cd services/api-rust
# Windows/vcpkg env vars needed for the native pq bindings:
$env:VCPKG_ROOT = "C:\vcpkg"; $env:VCPKGRS_DYNAMIC = "0"; $env:VCPKGRS_TRIPLET = "x64-windows-static-md"
cargo run                      # daily dev workflow — native, fast
cargo run --bin datagen        # seed ~10 fake profiles (User+Profile+Preferences+generated photos), password123, idempotent
                               # re-running also backfills photos on seed profiles that have none
cargo run --bin datagen -- --me you@example.com yourpass "Your Name" "City"   # seed just your own account
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings
cargo build --locked --all-features
cargo test --locked --all-features
```

Requires a `.env` with `DATABASE_URL` using `127.0.0.1` (not `localhost`). **`services/api-rust/DEPLOY.md` is the step-by-step for deploying to Railway** (root directory, env vars, the volume the photos need, and what breaks without each one). DB: `docker compose up -d db` (only the DB runs in Docker for normal dev; `docker compose up -d --build api-rust` is only for the occasional Dockerfile sanity check or real deploys).

Diesel migrations (schema changes):
```powershell
diesel migration generate name_of_change
# hand-edit up.sql / down.sql
diesel migration run --database-url "postgresql://matchpoint:matchpoint@127.0.0.1:5432/matchpoint"
```
Then hand-update `src/schema.rs` and `src/models.rs` (with `#[sql_name]` where needed — Diesel isn't auto-regenerating schema.rs, see below). `diesel.toml` must keep `[print_schema]` commented out, otherwise `diesel migration run` will regenerate `schema.rs` and wipe the manual annotations.

### Frontend (`apps/mobile/`)

```powershell
cd apps/mobile
flutter pub get
flutter analyze
flutter test
flutter run -d chrome     # or your emulator

# App icon — only when the icon or the palette changes:
dart run tool/gen_app_icon.dart      # draws assets/icon/*.png (see below)
dart run flutter_launcher_icons      # fans them out to Android/iOS/web
```

**Cleartext HTTP is allowed for localhost only** (`android/app/src/main/res/xml/network_security_config.xml`, wired in from the main manifest). Since Android 9 a *release* APK gets no automatic cleartext exemption, so a build pointed at the local backend (`--dart-define=API_BASE_URL=http://localhost:3000`, which is how you check a change on a real phone before deploying) installed fine and then failed every request, looking exactly like a dead server. The exemption covers `localhost`/`127.0.0.1` (what the phone sees behind `adb reverse tcp:3000 tcp:3000`) and `10.0.2.2` (the emulator's host alias); everything else, production included, still requires HTTPS.

**Android release signing.** `flutter build apk|appbundle --release` signs with the keystore described in `android/key.properties`, which is **not in the repo** (`android/.gitignore` covers it, along with `*.jks`/`*.keystore`); the keystore itself lives outside the repo entirely (`~/keys/matchpoint-release.p12` on the original machine). If that file is missing, `build.gradle.kts` deliberately falls back to the debug key so a fresh clone can still run `--release` — which means **an APK built without it is not publishable**, silently. Check with `apksigner verify --print-certs` if in doubt: the release cert is `CN=MatchPoint, …, C=ES`, not `CN=Android Debug`. The keystore cannot be regenerated: lose it and the published app can never be updated again.

**Building an APK that actually works on a phone.** The deployed API is `https://matchpoint-production-bfd0.up.railway.app`, and `api.dart` falls back to `10.0.2.2:3000` (the emulator alias) when nothing is passed — so a release build without `--dart-define=API_BASE_URL=…` installs fine and then no request ever arrives, which looks like a server problem and isn't. Verify before shipping: `unzip` the APK and grep `lib/arm64-v8a/libapp.so` for the production host (should appear) and for `10.0.2.2` (should not). Two more habits worth keeping: **bump `version:` in `pubspec.yaml`** — a phone that already has build 2003 rejects a lower one with `INSTALL_FAILED_VERSION_DOWNGRADE` — and, on MIUI, install via `adb push` to `/data/local/tmp` + `pm install` (plain `adb install` is blocked by `INSTALL_FAILED_USER_RESTRICTED`, and `/sdcard` by SELinux). From Git Bash, prefix adb calls that use device paths with `MSYS_NO_PATHCONV=1` or the shell rewrites `/data/local/tmp` into a Windows path. The universal APK is ~55 MB; `--split-per-abi` gives ~22 MB for arm64, which matters when sending it to someone over chat.

**App identity is fixed.** `applicationId`/`PRODUCT_BUNDLE_IDENTIFIER` is `com.matchpoint.app` on both platforms. Changing it after the first Play release means shipping a *different* app — losing users, ratings and history — so treat it as immutable.

### CI (`.github/workflows/ci.yml`)

Three jobs, all triggered on every branch push: `backend` (fmt check, clippy `-D warnings`, build, test — against a real Postgres service container), `mobile` (analyze, test, `flutter build web --release`), `docker` (builds the `services/api-rust` image). Match these locally before pushing — clippy warnings and fmt diffs fail CI.

**Gotcha — `flutter analyze` exits 1 on `info`-level hints, not just errors.** There is no severity threshold: one `prefer_is_not_empty` suggestion is enough to fail the whole `mobile` job on its first step, before `test` or the web build ever run. This bit once and cost three red commits, because the hint had been printing on every local run for a whole session and kept getting waved through as "only an info" — it *looks* advisory in the terminal and is a hard failure in CI.

So the rule is: **`flutter analyze` must print `No issues found!`**. Anything else is a build break, whatever its label. `flutter analyze; echo $?` is the honest check; the summary line is not.

Two more habits worth keeping, both learned the hard way:

- **`flutter build web --release` is part of the job and is the step least likely to be run locally.** `analyze` and `test` catch type errors; the web build catches things they don't (a platform-specific import, an asset declared but missing). Run it before pushing mobile changes, not just the other two.
- **Committing only one side still runs CI for both.** Backend-only commits were green on `backend` and red on `mobile` for days, because the mobile fix sat uncommitted in the working tree. A green local checkout proves nothing about what is pushed: to check what CI will actually see, reproduce the *committed* state — `git worktree add --detach <tmp> HEAD` gives it without disturbing uncommitted work.

## Backend architecture

`api-rust` is a straight port of a former NestJS app, and the module shape still mirrors Nest's DI structure — useful mental model when navigating:

- `src/main.rs` — thin entrypoint, just calls `matchpoint_api::run()`.
- **Gotcha — the listening socket is built by hand (`bind_dual_stack` in `lib.rs`), not with `TcpListener::bind`.** It has to accept IPv6 *and* IPv4: Railway's private network is IPv6-only (a process bound to `0.0.0.0` is alive but nobody talks to it, and the symptom is a "healthcheck failure" with no error in the log), while local dev comes in entirely over IPv4 (`127.0.0.1:3000`, and the `adb reverse` a wired phone uses). `bind("[::]:port")` alone doesn't do it: it works on Linux because `bindv6only` defaults off, but **on Windows it defaults on** and the socket silently refuses IPv4. Hence `socket2` with `set_only_v6(false)`.
- `src/migrate.rs` — migrations are **compiled into the binary** (`embed_migrations!`) and applied at startup, before the pool is built. A deploy has no shell to run `diesel migration run` in, and a service happily serving against a stale schema fails in confusing ways instead of failing clearly. Set `RUN_MIGRATIONS=false` to opt out. Local dev still uses the diesel CLI — the embedded copy is read at compile time, so a new migration needs a rebuild to be picked up.
- `src/lib.rs` — real startup logic (tracing init, config load, DB pool + connectivity check, CORS, router bind/serve). Everything is `pub mod`-ed here rather than in `main.rs` so app types count as "used" library surface for `cargo clippy --all-targets` (a bin-only crate would false-flag model types as dead code).
- `src/app.rs` — equivalent of `app.module.ts`: builds the root `Router` by `.merge()`-ing every feature module's router, then `.with_state(AppState)`.
- `src/state.rs` — `AppState { db: DbPool, config: Arc<AppConfig>, rate_limiter: RateLimiter, mailer: Mailer, pusher: Pusher }`, cloned into every handler (Axum's answer to Nest's constructor DI).
- `src/config.rs` — equivalent of `ConfigModule`: reads all env vars once at startup into `AppConfig`, panics fast if something required is missing. Also holds `AppConfig::validate`, which checks the things that are merely annoying in dev and a hole in production (repo-published example secrets, empty `CORS_ALLOWED_ORIGINS`, a `PUBLIC_BASE_URL` still pointing at localhost): it **warns** under `APP_ENV=development` and **refuses to boot** under `APP_ENV=production`. `.env.example` documents every variable — keep it in sync when adding one.
- `src/db.rs` — Diesel-async connection pool (bb8).
- Each feature module (`auth/`, `discover/`, `me/`, `swipes/`, `matches/`, `proposals/`, `notifications/`, `chats/`, `users/`, `admin/`, `app/`) follows the same three-file shape as its Nest ancestor: `controller.rs` (Axum router + handlers, maps errors to `StatusCode`), `service.rs` (business logic, DB queries), and `dto.rs` where request/response shapes need their own types. `auth/` additionally has `jwt.rs` (sign/verify) and `rate_limit.rs` (in-memory per-IP sliding-window limiter, applied only to `/auth/login|register|email-available`); `chats/` additionally has `crypto.rs` (AES-256-GCM message encryption — ciphertext at rest, plaintext over the API).
- `src/models.rs` / `src/schema.rs` — Diesel models and schema, hand-maintained (see migrations note above; do not expect `schema.rs` to auto-regenerate).
- `src/bin/datagen.rs` — extra binary in the same crate (auto-discovered by Cargo, no `Cargo.toml` change needed) for seeding test data; see Commands above. Its `mod photo` draws each seed profile's photos (a clay court / running track in perspective, 1280×720) with the `png` crate and writes them to `PHOTOS_DIR`. They're generated rather than downloaded so seeding works offline and is deterministic — and they're needed at all because `/discover` now hides profiles with no photo, which would otherwise erase the entire seed data set from the app. `png` is in `[dependencies]` only for this.
- `src/http_error.rs` — the single rule for error bodies: a 4xx keeps its own message, a 5xx logs the detail and returns one generic phrase. Every controller goes through `http_error::respond` instead of serialising `err.to_string()`, which used to leak `Database error: duplicate key value violates unique constraint "Swipe_fromUserId_toUserId_sport_key"` straight to the client.
- `src/push.rs` — FCM HTTP v1 push. `Pusher::{Log, Fcm}` mirrors `Mailer`: **without `FCM_SERVICE_ACCOUNT` it logs the notification instead of sending it**, so the flow is developable without credentials. Sends happen through `spawn_notify` (fire-and-forget — a push that fails must never fail the request that caused it), and a `Delivery::Stale` prunes the dead `DeviceToken` row. `parse_service_account` accepts the JSON raw or base64-encoded and un-escapes `
` in the private key, because pasting a multi-line PEM into a Railway variable mangles it.
- `src/mail.rs` — `Mailer::{Log, Resend}`, same "no credentials → log it" shape.
- `src/openapi.rs` — OpenAPI spec aggregator (`utoipa`), served as Swagger UI + JSON via `app.rs`. See "OpenAPI docs" below.

### Auth & data model

- JWT access/refresh: access token lives 15 min, refresh 30 days. Authenticated routes take `Authorization: Bearer <accessToken>`. Refresh tokens rotate on every use (old one deleted, new one issued) — the mobile client stores both tokens and `ApiClient` transparently refreshes-and-retries on a 401.
- **Gotcha:** `auth/service.rs` SHA-256-digests a refresh token before bcrypt-hashing it for storage (`refresh_token_digest`) — do not bcrypt-hash a raw token directly. bcrypt only looks at the first 72 bytes of its input, and two refresh JWTs for the same user share an identical prefix well past that (header + `sub` + `email` claims are byte-identical; only `exp`, near the end of the payload, differs), so bcrypt would treat every token ever issued to a user as equal to the current one — silently defeating rotation.
- DB table/column names are PascalCase/camelCase, inherited from the original Prisma schema — intentionally not renamed when porting to Diesel, so expect `#[sql_name]` annotations in `models.rs` rather than idiomatic snake_case.
- Core tables: `User`, `Profile` (1:1 via `userId`; includes nullable `latitude`/`longitude` set via manual place-search, Hinge-style — `city` doubles as the display name of the chosen place — nullable `gender`, nullable `intention`, and `availability`), `Preferences` (1:1 via `userId`), `RefreshToken`, `Swipe` (unique per `fromUserId,toUserId,sport`), `Match` (unique per `userAId,userBId,sport`), `Message` (ciphertext in DB, decrypted plaintext in API responses), `Proposal` (a concrete plan to play, hanging off a `Match`), `SessionFeedback` (one row per person per proposal — did you play, who won, would you repeat), `DeviceToken` (FCM tokens, one per device), `Report` (moderation queue).
- **`Profile.availability` is an `INTEGER` bit mask, not an enum.** 21 bits, `bit = day * 3 + band` (Monday first; morning/afternoon/night). It says what someone *usually* has free.
  - **It now filters and orders `/discover`** — this reverses the 2026-08-23 decision that took it out of the ordering, and the reversal is deliberate (see `overlap_rank` in `discover/service.rs` for the full argument). Short version: back then it was a coarse six-value enum filled in during onboarding and shown on no screen, so ordering "who you meet" by it meant deciding with data nobody had looked at. Now it is an editable 21-slot grid, visible on the profile, and — the part that changes the argument — **it is what the viewer explicitly asked for** in the "cuándo puedes jugar" filter. What survives of the old caution is the distrust of precision: the ordering buckets the overlap at 0/1/2/3-or-more instead of using the raw count, so marking the whole week doesn't win.
  - It is still a reference and not a calendar in the **propose** flow, where it only dims days/hours and blocks nothing. Mobile side: `WeeklyAvailability` in `features/onboarding/models/availability.dart`.
- Enums: `Sport` (TENNIS, RUNNING), `SwipeType` (LIKE, PASS), `SkillLevelValue` (also `PartialOrd`/`Ord` — `goal_fit` compares levels), `Gender` (MALE, FEMALE, OTHER), `ProposalStatus` (PENDING, ACCEPTED, DECLINED, CANCELLED), `Intention` (COMPETE, TRAIN, LEARN, FUN), `SessionOutcome` (won/lost/draw, tennis only).
- **Gotcha — partial PATCH and nullable fields:** the usual `.or_else()` merge in `me/service.rs` cannot tell "field omitted" from "field sent as null", so a plain `Option<T>` DTO field can be set but never *cleared*. Fields the user must be able to unset (`Profile.gender` → "prefiero no decirlo", `Preferences.genderPreference` → "cualquiera") use `Option<Option<T>>` with the `double_option` deserializer in `me/dto.rs`. On the mobile side those go through dedicated methods (`updateGender`, and `genderPreference` being a `required` param of `updatePreferences`) that always send the key, instead of the `'key': ?value` idiom that would drop it.

### API surface

- Auth: `POST /auth/register|login|refresh|logout`, `GET /auth/email-available?email=`, `POST /auth/send-verification` + `POST /auth/verify-email { code }` (ambos autenticados: así el código sólo puede pedirse para la propia cuenta y nadie puede usarlo para bombardear el buzón de otro). Código de 6 dígitos, 15 min de vida, 5 intentos y 60 s de cooldown entre reenvíos; se guarda su SHA-256, no el código. `/me` expone `emailVerified`. El envío va por `mail::Mailer`, que **sin `RESEND_API_KEY` escribe el correo en el log en vez de enviarlo** — eso es lo que permite desarrollar el flujo sin credenciales. **`EMAIL_VERIFICATION_ENABLED=false` lo apaga entero**: los endpoints responden 503 y `/me` expone el flag para que el cliente esconda la pantalla. Existe por una limitación real — sin un dominio de correo verificado, Resend (y cualquier proveedor) sólo entrega al titular de la cuenta, así que con esto encendido cualquier otra persona que se registre choca contra un fallo de envío nada más crear la cuenta. Va por el servidor y no por una constante del cliente para poder encenderlo el día que haya dominio sin publicar una versión nueva de la app. `login`/`register`/`email-available` are rate-limited (10 req/60s per IP, 429 past that).
- Me: `GET /me` (expone `emailVerified` y `emailVerificationEnabled`), `DELETE /me` (borra la cuenta entera; las tablas cuelgan de `User` con `ON DELETE CASCADE`, pero los **ficheros** de las fotos no los borra ningún cascade y hay que quitarlos a mano), `PATCH /me/profile` (does **not** accept `photos` — that field only exists on the dedicated photo endpoints below), `PATCH /me/preferences`, `POST /me/photos` (multipart, enforces `MAX_PHOTOS`=6 + type/size validation — it sniffs the actual bytes rather than trusting the declared content-type), `DELETE /me/photos` (can't delete the last photo)
- Discover: `GET /discover?sport=TENNIS|RUNNING&availability=<21-bit mask>&level=<SkillLevelValue>` — **400s if the caller doesn't play the requested sport** (the filter used to apply only to candidates, so asking for `?sport=RUNNING` as a tennis-only player returned runners and produced matches with no sport in common — matches that can never become a session, since proposing requires both to practise it). With no `?sport=`, candidates must overlap at least one of your sports. Also excludes already-swiped users — but **a PASS expires after `PASS_EXPIRES_AFTER_DAYS` (30) and that person comes back**, while a LIKE hides forever. A permanent PASS empties the feed for good at this app's real density (tens of people per town, not thousands): two evenings of swiping and there is nobody left, ever. `create_swipe` rewrites `created_at` on its upsert so re-passing restarts the window instead of dragging the first rejection's date. Requires a **complete** profile (at least one photo *and* coordinates: an incomplete card is just a blank to dismiss, and onboarding no longer lets you finish without either), and filters by the caller's `ageMin`/`ageMax`, `distanceKm` and `genderPreference` (age falls back to 18-60 with no preferences row; distance via Haversine, no PostGIS). Two deliberate "don't punish missing data" carve-outs remain: a **viewer** with no coordinates isn't distance-filtered at all, and a candidate who hasn't stated a gender is never excluded by the gender filter. Each result also carries three viewer-relative fields computed here and **nowhere else** (they must not leak from `/users/:userId/profile` or the `otherUser` side of `/matches`, which hardcode them to false/None): `distanceKm` (the derived number — raw coordinates never leave the server), `matchesYourLevel`, and `likesYou`. Each result also carries `sharedAvailability`/`sharedSlots` (the viewer's weekly grid AND-ed with the candidate's, plus its popcount) — same viewer-relative rule as the three above, so they are forced to 0 elsewhere. `?availability=` keeps only candidates overlapping the mask in at least one slot, and **does exclude people who never filled their grid in** — unlike the gender/coordinates carve-outs, because here the viewer asked a direct question ("who can play Saturday?") that an empty grid cannot answer. A mask of `0` means "no filter", never "nobody". The feed is then ordered by `(!likesYou, Reverse(overlap_rank), Reverse(goal_fit), distance)` — people who already liked you first, then whoever you can actually coincide with, then whoever best fits what you came for, then the nearest. Capped at 50 (was 20: the screen stopped being a three-card deck). **`goal_fit` inverts the level rule for `Intention::Learn`**: someone who says they want to improve was being shown "people at your level", i.e. the opposite of what they asked for, so for them a *better* candidate scores highest. Availability is deliberately **not** part of this order (see the `Profile.availability` note above). **Which sport to ask for is the client's call**, taken from `Preferences.sportsWanted` (falling back to the user's own `Profile.sports`) — the endpoint itself just honours the `?sport=` it's given.
- Swipes: `POST /swipes { toUserId, sport, type: LIKE|PASS }` → `{ match, matchId?, swipeId }`. **The reciprocal LIKE that forms a match is looked up across all sports, not just the one being swiped.** Each side independently picks which feed it's browsing, so two people who both play both sports would routinely like each other on *different* sports and never match — while "te ha dado like" still showed up, promising a match that never came. A like means "I want to play with you", and since `/discover` only shows people you share a sport with, a reciprocal like already implies a common sport. `likesYou` in `/discover` is unfiltered by sport for the same reason. Before inserting, an existing match between the pair on *any* sport is returned instead — the table's unique key is (userA, userB, sport), so without that check two people who play both would end up with two matches and two separate chats.
- Matches: `GET /matches` (includes `sport`, `lastMessage` decrypted preview + `unreadCount` per match), `DELETE /matches/:matchId` (unmatch — deletes the match + its chat; only a match member can call it). **It also turns both sides' LIKE swipes into PASS dated now**: deleting the match used to leave the two LIKEs standing, and a LIKE hides someone forever, so undoing a match made the pair mutually invisible for life — including the person who didn't undo anything. As PASSes they expire like any other rejection. To cut contact permanently there's Report, which a human reviews.
- Proposals: `POST/GET /matches/:matchId/proposals`, `PATCH /proposals/:proposalId { action: ACCEPT|DECLINE|CANCEL }`, `GET /me/proposals` (the caller's whole agenda: `ACCEPTED` **and** `PENDING`, still upcoming, across all matches — pending ones are included because otherwise a proposal you hadn't opened yet was reachable only from inside the chat that carried it, i.e. invisible in the one screen that answers "what do I have on?"; the client groups by `status`). Four rules worth knowing before touching `proposals/service.rs`: **`Match.sport` does not decide what you can propose** — what matters is which sports *both* people play (`assert_both_play`), i.e. the intersection of the two profiles. In practice that means: one of you plays a single sport → only that one (which is necessarily the match's, since you had to share it to match at all); both of you play both → either one, in the same conversation, instead of needing a second match with the same person; creating a proposal **cancels any still-pending one in that match** (a counter-offer is implicitly a "no" to the previous one); only the *recipient* may accept/decline, and only while `PENDING` (propose again rather than un-declining, so history stays honest); and `CANCEL` is the one action that also works on an `ACCEPTED` session — by *either* side, since plans change and forcing someone to just not turn up is worse.
- Notifications: `GET /me/notifications` → `{ unreadMessages, pendingProposals }`. Its own module because it spans chats + proposals; returns only counts, since the mobile client polls it every 15s while the app is open.
- Chats: `GET/POST /chats/:matchId/messages`, `PATCH /chats/:matchId/read` (403 if not a match member)
- Users: `GET /users/:userId/profile` (public profile, still requires auth; 404 if missing), `POST /users/:userId/report { reason }` (logs a report for review only — does not touch any match/chat)
- Proposals feedback: `GET /me/proposals/awaiting-feedback` + `POST /proposals/:proposalId/feedback` (upsert on `(proposalId, userId)`). Coherence rules live in `proposals/service.rs`: no result and no rating if you say you didn't play, and no win/lose outcome for RUNNING. `matches` counts `playedTogether` from these rows when **either** side said it happened.
- Admin (moderation + operations, all gated by `ADMIN_API_KEY` in the `X-Admin-Key` header): `GET /admin/reports`, `PATCH /admin/reports/:reportId`, `GET /admin/incomplete-accounts` + `DELETE` on the same path (accounts with no profile or no photos; never touches anyone who has a match), and `POST /admin/reset?confirm=BORRAR-TODO` (empties the whole installation — every account plus the photo **files**, which no cascade covers). Two conventions worth keeping: a wrong or unset key returns **404, not 401**, so probing URLs learns nothing; and the destructive endpoints take a separate confirmation (a distinct verb, or the literal `confirm` word) because the same key is used daily from a terminal to read the moderation queue.
- Density: `GET /discover/density?lat=&lng=&radiusKm=&sport=` → `{ count }`. **The only unauthenticated endpoint besides auth**, and it has to be: it feeds the onboarding location step, where no account exists yet (nothing is created until the last page of the wizard). It answers "is there anybody here?" *while* someone picks their location, instead of after they've filled five screens and uploaded a photo. Returns a number and nothing else — no profiles, no names, no positions — and sits behind the same per-IP limiter as `/auth/login`, so it's no use for enumerating anyone.
- Misc: `GET /`, `GET /health` (actually queries the DB with a 2s timeout and returns **503** when it can't — a liveness probe that always says `{ok:true}` is worse than none)

There's no *computed* rating yet (Elo vs Glicko-2 undecided) — `discover` has self-reported `SkillLevel` but nothing to rank by actual results. `Proposal` is the hook that unblocks it: an accepted, already-played session is the thing whose result you'd record.

There's no Block feature — deliberately removed (see git history on `feature/rust-backend`); unmatch (cuts contact) + report (flags for review) were judged to cover what block would have.

### OpenAPI docs

Swagger UI at `http://localhost:3000/docs`, raw spec at `/api-docs/openapi.json` (`utoipa` + `utoipa-swagger-ui`, mounted in `app.rs`). When adding an endpoint: derive `ToSchema` on its DTO/response types, add a `#[utoipa::path(...)]` block above the handler (copy a neighboring one in the same `controller.rs` as a template), then register the handler and any new schema types in `src/openapi.rs`'s `paths(...)`/`components(schemas(...))`. Missing/mismatched entries fail `cargo build`, so the docs can't silently drift from the code.

**Gotcha:** in `request_body`/`responses(body = ...)`, always reference the type by its **short name** (`body = MeResponse`), never a fully-qualified path (`body = crate::me::service::MeResponse`) — with utoipa 4.x the latter produces a broken literal `$ref` (`crate.me.service.MeResponse`) that doesn't match how the type gets registered in `components/schemas` (by short name), and Swagger UI shows "could not resolve reference" errors. This means the short name has to be `use`-imported into `controller.rs` purely for the macro, which clippy then flags as `unused_imports` since nothing else in the file references it by that path — put `#[allow(unused_imports)]` above that `use` (every `controller.rs` already does this; copy the pattern).

**Gotcha:** `utoipa-swagger-ui`'s build script downloads the Swagger UI static assets at compile time via the system `curl` binary. `services/api-rust/Dockerfile`'s builder stage (`rust:1-slim-bookworm`) installs `curl` + `ca-certificates` for this — don't remove them, `cargo build --release` inside the image fails without them (`utoipa-swagger-ui` build script panics: `curl` not found).

## Frontend architecture

**The app is tennis-only, and running is switched off rather than deleted** (`core/utils/app_sports.dart`). `enabledSports` is the single source of truth; `singleSport`/`isSingleSportApp`/`onlyEnabled()` are what every "should I show the sport?" question must ask, instead of comparing against `Sport.tennis` inline — turning the second sport back on has to be one line, not a hunt. The enum, the `Profile.sports` column, the `?sport=` filter and running sessions all still exist server-side, so the switch is reversible; a destructive migration to undo a product decision that may well change would not be.

What the switch actually hides: the sport step in onboarding, the sport chips in the Discovery preferences sheet and on list rows, the "Deportes" row in Settings (the last door left for marking running), the running-only credential fields, and the per-sport propose buttons in chat. `onlyEnabled()` also clamps accounts created back when running was pickable.

**Onboarding is 5 pages, location first** (`features/onboarding/screens/onboarding_profile_screen.dart`): Ubicación → Perfil → Tu juego (level + weekly grid) → Foto → "Así te van a ver". Location leads because it is the only question that can answer *is there anyone here*, and the step asks `/discover/density` while you pick, so a dead zone says so up front instead of after five screens and a photo upload. What left the wizard: choosing a sport (there is one), credentials (years/club/achievements — for showing off, not for matching, and Settings has them), and the whole preferences page (age range, gender preference, intention — filters with sane defaults that in an empty app only make it emptier; all still in Settings).

`apps/mobile/lib/` is feature-organized:
- `app/` — app shell, routing (`router.dart`, `routes.dart`).
- The launcher icon is **derived from `tool/logo_source.png` by code, not exported from an image editor**: `tool/gen_app_icon.dart` reads that logo and writes the three PNGs under `assets/icon/` — `app_icon.png` (opaque; iOS/web/legacy Android), plus `app_icon_background.png` / `app_icon_foreground.png`, the two Android adaptive-icon layers. It decodes and encodes PNG by hand (`dart:io` already ships zlib), so no image package is involved; same reasoning as `datagen`'s generated seed photos. **The source is still the two-halves logo (racket | shoe), but the icon is now tennis-only**: the generator isolates the racket, re-centres it by its bounding box, and fills the background with one flat clay orange from `core/utils/sport_words.dart` — the divider goes with the shoe, since with one half there is nothing to divide. Nothing is redrawn or cropped by hand: the artwork mask (each pixel projected onto the background→white line, which inherits the source's antialiasing instead of rebuilding it with a threshold) already separates drawing from background, so the racket is measured out of it. Re-exporting the logo at another size still requires touching no number here.

`AppLogo` (Welcome, login/register) renders `app_logo.png`, generated from the same source in the same run, so the launcher icon and the in-app logo can't drift apart.

**Gotcha — one constant governs three outputs, and the adaptive safe zone is the binding one.** `_launcherArtFraction` (0.58) is how much of the canvas the racket spans; the adaptive foreground divides it by `_adaptiveInset` (0.68) because Android draws that layer inside a 16% inset that `flutter_launcher_icons` writes into the XML. The arithmetic that picks 0.58 is written out in the constant's doc comment: it lands the racket tip at 31.3dp from centre, inside the 66dp circle Android guarantees never to clip. At 0.62 it came out at 67dp and an aggressive launcher mask could shave the head or the butt of the handle. Verified by simulating the real composition (background + inset foreground, clipped with circle and squircle masks), not by eye.

**Gotcha — the notification icon can't use the strings.** Android paints it monochrome at 24dp. The old one was the logo's circle with the divider cut, because a racket *and* a shoe got twelve pixels each and turned into two smudges; with one drawing that problem is gone, but the string grid still dissolves into grey at that size. So `_notificationIcon` **fills** the racket by horizontal span (first to last artwork pixel per row), which closes the mesh without touching the outline or rounding off the handle the way a dilate/erode would.
- Photos are always stored and shown in 16:9 landscape. `core/utils/landscape_crop.dart` centre-crops with `dart:ui` (no extra dependency; same code path on mobile and web, and it uses the GPU instead of walking pixels in Dart) and re-encodes to PNG, so the uploaded filename/content-type must be set to `.png`/`image/png` rather than the picker's originals. The photo sheet has a third way out besides camera and gallery: **six illustrated avatars shipped in `assets/avatars/`** (`core/ui/profile/avatar_gallery.dart`). A profile needs at least one photo to appear in `/discover`, and that requirement in front of someone who just installed the app is where people quit — so the avatar is the escape hatch, offered in the onboarding step's own copy and not only inside the sheet. An avatar goes through the same 16:9 crop as any photo (one code path when the crop changes) but skips the preview, since it was just chosen from a grid. `pickPhotos` therefore returns a `PhotoPick` (files **or** an avatar asset), not a bare `List<XFile>`. Both upload entry points (onboarding and the photo manager sheet) go through `showPhotoCropPreview` first — which takes a **list** (`pickMultiImage`), previews every crop at once and lets the user drop individual ones, because doing this one photo at a time is the very first thing a new user has to sit through. Profiles show every photo stacked vertically at 16:9 (`ProfileView`, the Discovery preview sheet and the onboarding "así te van a ver" step), not a side-swipe carousel: the carousel hid every photo but the first behind a gesture nothing advertised.
- **Gotcha — `ChipThemeData.labelStyle` needs an explicit colour.** It does *not* go through the `.apply(bodyColor: ...)` that `ThemeData` runs over `textTheme`, so a label style declared without a colour leaves the colour null all the way down and Flutter's engine falls back to its own default, which is **white** — every chip label in the app was invisible on light backgrounds. `app_theme.dart`'s `_chipTheme` sets it via `WidgetStateColor` (selected vs not vs disabled), plus a matching `iconTheme`. Same trap applies to any `TextStyle` handed to a component theme rather than to `textTheme`.
- Weekly availability is a 7×3 grid (`core/ui/widgets/availability_picker.dart`): `AvailabilityPicker` to fill it in (drag-paint — 21 cells tapped one by one is exactly the friction that stops anyone filling it), `AvailabilityView` to read someone else's. It shows up in onboarding, Settings, the profile, and — the reason it exists — inside the propose flow: `WeekCalendarPicker` greys out the days the other person doesn't usually have free and `pickTimeSlot` dims the hours outside their bands *for that day*. Neither one blocks: it's a reference, not their calendar. **The 14:00/20:00 cut between bands lives in `WeeklyAvailability.bandOfHour` and nowhere else** (a test pins it) — if it drifts from the grid, the hour picker dims hours the other person actually marked.
- Wording for a session lives in `core/utils/sport_words.dart` (`sportSessionTitle`/`sportSessionNoun`/`sportIcon`). It exists because the app used to interleave tennis and running, where "partido" is wrong half the time — hence the neutral umbrella term **quedada**. With running switched off the umbrella is gone from the UI (the tab is "Tus partidos" again) but the helper stays: it is what makes turning the second sport back on a one-line change.

- **A proposal is a message, and it lives in the chat timeline** (`core/ui/widgets/proposal/proposal_bubble.dart`). It used to be pinned above the conversation in a half-screen block — put there because the original failure was proposing via plain text that scrolled away, but overcorrected: it covered the chat, and a resolved proposal stayed nailed there with nothing to do. Now proposals are interleaved with messages, **sorted by `createdAt`, not `scheduledAt`** (a proposal made today for next month belongs where it was written), aligned by sender, and a cancelled one stays in place struck through.
  - Fixed width and always three lines, place included (`Sin sitio concreto` when there is none): these are cards, not text bubbles, and one that resizes with its headline reads as a different kind of thing.
  - **Resolved proposals are outlined, not filled, and are not tappable** — there is nothing to do inside, and opening a screen with no actions is a dead end.
  - Tapping a live one opens **`SessionDetailScreen`, the same screen the Partidos tab opens.** A separate sheet was written for this once and deleted: it showed the same content in a different shape, and two screens for one thing drift apart — which had already happened with the state colours.
- **`proposal_state_style.dart` is the single source for what a proposal's state looks like** (icon, colour, headline). The chat bubble fills its whole background with it; the Partidos row tints only when `wantsAttention`. Before this existed, the same `PENDING` was lime in the chat and a green border in Partidos. Note the distinction the file encodes: a proposal awaiting *your* answer and one where *you* are waiting are both `PENDING` but only one asks anything, so only one gets the loud colour.
- `core/` — cross-feature: `network/` (`api_client.dart` — HTTP client with transparent 401-refresh-and-retry, `api.dart` — backend base URL/singleton), `auth/` (`auth_gate.dart`), `storage/` (`token_storage.dart` — access + refresh tokens, secure storage), `theme/`, `ui/` (shared widgets: `ui/widgets/` has per-feature subfolders like `chat`, `discovery`, `matches`, `onboarding`; `ui/dialogs/` has generic confirm/report dialogs; `ui/profile/` has profile-display widgets shared between own/other profile screens).
- **The three tab screens share one header** (`core/ui/widgets/screen_header.dart`): big bold left-aligned title, actions on the right, and a **minimum height** so a screen without buttons is not shorter than the others. That last part is not cosmetic — an `IconButton` is 48dp, so Partidos (the only one with no actions) collapsed to 60dp against the others' 72 and read as "smaller title, sitting higher". A test pins it. Before this widget existed Discovery painted its own copy of the same header, which is how they drifted in the first place.
- **Discovery is a search, not a deck** (`features/discovery/screens/discovery_screen.dart`). The filter bar (`core/ui/widgets/discovery/discovery_filter_bar.dart` + `when_filter_sheet.dart`) sits *above* the results rather than behind a funnel icon, because "cuándo puedes jugar" is the question, not a fine adjustment — hidden, the screen goes straight back to being a deck of faces with an options button. Results are `PlayerListTile`s that lead with the slots you share, then level and distance, with the photo as a thumbnail and two named buttons instead of a drag (in a list that scrolls under the thumb, a horizontal drag fights the scroll). The old staggered card deck is still there behind the toggle in the header — it's more fun than the list and worse for deciding, which is why it's the secondary mode. `DiscoverFilters` carries the state; empty results now offer a way out (clear filters / widen the radius) instead of dead-ending.
- `features/` — one folder per feature (`auth`, `discovery`, `matches`, `onboarding`, `profile`, `welcome`, `courts` — tennis club map, `flutter_map` + OSM tiles, Overpass API for real club data, entered from the AppBar on Matches). **Gotcha in `OverpassService`:** tennis courts (`leisure=pitch`) almost never carry a `name`, and most Spanish clubs' `leisure=sports_centre` carries no `sport` tag either — so asking for `sports_centre` *with* `sport~tennis` finds almost nothing (3 named results out of 79 named facilities near Benalmádena). It therefore fetches **every** facility in the radius and attaches its name to any court cluster within 300 m, refusing facilities whose `sport` tag names a different sport (courts next to "Karting Mijas" must not inherit that name). Don't add a `name~"[Tt]enis"` clause — a name regex over a 15 km radius makes Overpass return 504., each with its own `models/`, `screens/`, `services/`.
